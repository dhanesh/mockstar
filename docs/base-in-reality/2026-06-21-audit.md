## Executive summary

Six falsifiable design claims were carried through verification across mockstar's security-, crypto-, reliability-, and algorithm-sensitive surfaces. After an adversarial refutation pass:

- **1 confirmed DEVIATION (medium)** — the SSRF guard validates the URL hostname *string* but never resolves DNS, so a public hostname pointing at a private/metadata IP bypasses the private-range rejection. Real and grounded in OWASP; severity moderated to **medium** because the trust boundary is operator-authored config on a local dev tool, with an opt-in escape hatch and an in-code admission of the limitation.
- **2 confirmed DEVIATIONS (low / info)** — the webhook circuit breaker admits a small burst of concurrent probes in half-open instead of a single trial (Fowler / Microsoft pattern); and a hot-path comment mislabels a segment prefix-trie as a "radix-trie … O(log n)".
- **1 candidate VIOLATION did NOT survive refutation** — the deterministic ID generator's 32-bit seed *looked* like it contradicted the "0 collisions over 1M" invariant, but that invariant (O6) is tested and scoped to the **crypto-backed** mode (space 62¹⁴ ≈ 1.24e25), not the deterministic mode. **Downgraded to `UNCONFIRMED`.** This is the adversarial gate working as intended.
- **1 verified-sound** — webhook HMAC-SHA256 signing matches Stripe's documented scheme (signed payload `timestamp.body`, constant-time compare, 5-minute replay tolerance). No action.
- **1 dropped as noise** — symmetric retry jitter vs. AWS "full jitter"; a defensible engineering choice, not an actionable finding.

Net: **the codebase is in good shape against real-world norms.** The one finding worth acting on is the SSRF DNS-resolution gap; the rest are low-stakes accuracy/robustness polish.

## Findings (ordered by severity, then layer)

### F1 — SSRF guard validates hostname string, never resolves DNS · `DEVIATION` · **medium**

- **Layer:** biz / security
- **Location:** `src/features/url-validator.ts:58-67,70-111` (call sites: `pass-through.ts`, `webhooks/dispatcher.ts`, `openapi/converter.ts`)

`validateUpstreamUrl` → `isPrivateHost` inspects only the hostname **string**: a scheme allowlist plus rejection of literal private/loopback/link-local IPs. For any non-IP-literal hostname it falls through to `return false` (line 110), with an explicit comment that "DNS rebinding attacks are out of scope for an OSS dev tool" (lines 108-109). No call site re-checks the **resolved** IP at connect time. Consequently a public hostname whose DNS A-record points at `169.254.169.254` (cloud metadata) or `127.0.0.1` passes validation — the classic DNS-based SSRF bypass.

**Refutation result:** correctness lens **upheld** (mechanism confirmed; no second-line IP check exists at any call site). Citation-applicability and severity lenses **refuted the original "high"**: OWASP targets production handlers proxying anonymous-client URLs, whereas here upstreams are operator-authored mock config on a developer's machine, private targets require `allowPrivateUpstreams` opt-in, and the limitation is self-documented. Net: a **real** deviation, severity moderated **high → medium**.

**Citations (fetched):**
- OWASP SSRF Prevention Cheat Sheet — <https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html>
  > "the application will retrieve all the IP addresses behind the domain name provided (taking records A + AAAA for IPv4 + IPv6) and it will apply the same verification described in the previous point about IP addresses."
  > "Monitor the domains allowlist in order to detect when any of them resolves to a … Local IP address (V4 + V6)."

**Recommended fix:** resolve the host to all A/AAAA records inside `validateUpstreamUrl`, run each resolved IP through `isPrivateIpv4`, then pin the validated IP for the actual fetch (or re-validate at connect time via a custom socket `lookup`) to also close the TOCTOU/rebinding window. Keep `allowPrivateUpstreams` as the opt-in. If full DNS validation stays out of scope by design, narrow the gap with an explicit upstream-host allowlist for pass-through / OpenAPI `servers.url`, and keep the SECURITY.md disclosure.

**Remediation — FIXED (2026-06-21).** Added `validateUpstreamUrlResolved` / `assertResolvedHostPublic` to `url-validator.ts`: after the synchronous string-level guard, it resolves the hostname (A + AAAA, injectable resolver) and rejects if **any** resolved address is private/loopback/link-local; it fails closed on resolution error or empty result, and short-circuits for IP-literal hosts and the `allowPrivateUpstreams` opt-in. Wired into both fetch sites — `pass-through.ts` (request time) and `webhooks/dispatcher.ts` (per-attempt). Covered by 10 new tests in `tests/url-validator.test.ts` (incl. the `evil.example.com → 169.254.169.254` metadata bypass). The narrow DNS-rebinding (TOCTOU) window between our resolution and `fetch()`'s own resolution remains documented in-code as an accepted residual for a dev tool; full closure would require socket-level IP pinning.

### F2 — Circuit breaker half-open admits a burst of concurrent probes · `DEVIATION` · **low**

- **Layer:** arch / reliability
- **Location:** `src/features/webhooks/circuit-breaker.ts:40-45,56-60`; consumer `src/features/webhooks/queue.ts:63,193-194`

`gate()` flips OPEN→HALF_OPEN on cooldown elapse and then returns `"half-open"` for **every** subsequent call until a `record()` outcome arrives — there is no single-probe counter or in-flight trial cap. The queue only short-circuits on `"open"` (line 193), so half-open falls through to a real `attempt()`. With `DEFAULT_CONCURRENCY = 8`, up to ~8 concurrent trial deliveries can hit a still-unhealthy upstream the instant cooldown expires, before the first failing `record()` re-trips the breaker.

**Refutation result:** **upheld** (low). The canonical pattern admits a single/limited trial; the consumer does not limit probes, so the framing is correct, not an over-read. Severity stays low — exposure is bounded by the concurrency cap (one ~8-wide burst) and self-corrects on the first probe outcome.

**Citations (fetched):**
- Martin Fowler, *CircuitBreaker* — <https://martinfowler.com/bliki/CircuitBreaker.html>
  > "Asked to call in the half-open state results in a trial call, which will either reset the breaker if successful or restart the timeout if not."
- Microsoft, *Circuit Breaker pattern* — <https://learn.microsoft.com/en-us/azure/architecture/patterns/circuit-breaker>
  > "Half-Open: A limited number of requests … are allowed to pass through … The Half-Open state helps prevent a recovering service from suddenly being flooded with requests."

**Recommended fix:** track outstanding probes when transitioning to HALF_OPEN; admit only N (N=1 canonical) trial requests — return `"half-open"` for the first N `gate()` calls after the transition and `"open"` thereafter until a `record()` resolves the probe.

**Remediation — FIXED (2026-06-21).** `gate()` is now an atomic acquire: it hands out at most `halfOpenMaxProbes` (default **1**) permits in half-open and returns `"open"` (deny) beyond that until a `record()` releases a probe. Added a non-consuming `peek()` and repointed `metricValue()` to it so metrics scraping never spends the probe budget. Five new tests in `tests/webhooks/circuit-breaker.test.ts` cover single-probe default, peek non-consumption, permit release, and `halfOpenMaxProbes > 1`. Full webhook suite (114 tests) green.

### F3 — Hot-path comment mislabels a segment prefix-trie as "radix-trie … O(log n)" · `DEVIATION` · **info**

- **Layer:** algo
- **Location:** `src/core/matching/path-trie.ts:1-2,19-46,60-89`

The header comment claims "radix-trie on method + path-pattern; O(log n) first-level dispatch". The structure is a per-**segment** prefix trie: literal children via `Map<string, node>` (O(1)-avg per segment), one param and one wildcard child, and a recursive backtracking `walk`. It has **no single-child edge compression** — the defining property of a radix/PATRICIA tree — and per-segment Map dispatch is O(1)-avg, not O(log n). Runtime behavior is fine; only the comment overstates an asymptotic guarantee in a component tagged "binding (hot-path latency)", which could mislead perf reasoning.

**Refutation result:** **upheld**, downgraded to **info** (comment-accuracy, not a runtime defect).

**Citation (fetched):**
- Wikipedia, *Radix tree* — <https://en.wikipedia.org/wiki/Radix_tree>
  > "a radix tree … is a data structure that represents a space-optimized trie … in which each node that is the only child is merged with its parent."

**Recommended fix:** reword to e.g. "segment prefix trie on method + path-pattern; O(1)-avg per-segment dispatch, multi-branch backtracking walk." Drop "radix-trie" and "O(log n)".

**Remediation — FIXED (2026-06-21).** Header comment in `path-trie.ts` corrected to "segment prefix-trie … O(1)-avg per-segment dispatch", with an added note that single-child chains are not compressed (so it is not a radix/PATRICIA tree) and that `findPath` cost is bounded by depth × branch factor, not log(n) of route count.

## Verified sound (no violation)

### S1 — Webhook HMAC-SHA256 signing matches Stripe's scheme · `UNCONFIRMED` (no defect)

- **Location:** `src/features/webhooks/signing.ts:18-21,30-44,47-55`

Signs `HMAC-SHA256(secret, ` + "`${timestampMs}.${rawBody}`" + `)`, verifies with `node:crypto.timingSafeEqual` behind a required equal-length guard, and enforces a default 5-minute replay window (+60s future skew). This matches Stripe's documented signed-payload construction, constant-time comparison requirement, and 300-second default tolerance.

**Citation (fetched):**
- Stripe Webhooks — <https://docs.stripe.com/webhooks.md>
  > "The signed_payload string is created by concatenating: The timestamp … The character `.` … the request body … Compute an HMAC with the SHA256 hash function. Use the endpoint's signing secret as the key … use a constant-time-string comparison … a default tolerance of 5 minutes."

**Note (non-defect):** the timestamp is in **milliseconds** vs. Stripe's seconds. Internally consistent (signer + bundled verifier agree); only matters if interoperating with a real Stripe-format receiver expecting Unix seconds. Worth a one-line doc note, not a fix.

**Superseded 2026-09-04 (see #30):** this claim verified the *signed-payload construction*
against Stripe and found it sound. It did not examine the emitted **header value**, which was
fixed at `{algorithm}={signature}` — GitHub's format, not Stripe's `t=...,v1=...`. The crypto
was correct; the delivered combination matched no single provider. Both axes are configuration
as of the signing-scheme change, and the millisecond-vs-seconds gap noted above is now covered
by `{timestampSeconds}`. Verified by `tests/webhooks/provider-fidelity.test.ts`.

## Did not survive refutation (downgraded)

### C2 — Deterministic ID generator "0 collisions over 1M" · ~~VIOLATION~~ → `UNCONFIRMED`

- **Location:** `src/core/templating/tier2/id.ts:2,35-36,96-103,106-119`

**Original claim:** deterministic mode seeds Mulberry32 from a 32-bit FNV-1a hash, capping entropy at 2³², so by the birthday bound ~116 colliding seed-pairs are expected over 1M draws — contradicting the header's "O6: 0 collisions over 1M at L=14". The birthday arithmetic itself is correct (`n²/2·2³² ≈ 116`, grounded in Wikipedia *Birthday problem* / *Birthday attack*).

**Why it was downgraded:** verified against the actual test — `tests/tier2-id.test.ts:34-44` runs the 1M-draw, zero-collision assertion inside the **`deterministic: false`** describe block (line 7-8), i.e. the **crypto-backed** path whose space is 62¹⁴ ≈ 1.24e25 (p(collision) ≈ 1e-14). The O6 invariant is *scoped to* and *validated in* crypto mode. The deterministic-mode tests (line 105+) assert reproducibility and cross-counter distinctness, never a 1M collision bound — its 32-bit seed deliberately encodes `requestCounter`, and its purpose is reproducibility, not global uniqueness. All three refutation lenses (correctness, citation-applicability, severity) refuted. The finding contradicted a claim the code does **not** make. Reported as `UNCONFIRMED` per the no-fabricated-violations rule.

**Residual low-confidence observation (not a finding):** if a caller ever relied on deterministic mode for cross-request *uniqueness*, two distinct `tenant|endpoint|counter` strings that FNV-1a-alias would yield identical ID streams. No code path or spec promises this, so it is recorded only for transparency. A one-line header clarifying that O6 covers non-deterministic mode would remove all ambiguity.
